# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The bridge for [Herdr](https://herdr.dev) (a terminal multiplexer for AI coding agents): a Rust daemon (axum + tokio) that translates between Herdr's Unix-socket JSON-RPC (`~/.config/herdr/herdr.sock`) and HTTP/WS on port 7788, for the apps that reach herdr from elsewhere: [herdr-mobile](https://github.com/XicuM/herdr-mobile) (Flutter, Android and Linux) and [herdr-obsidian](https://github.com/XicuM/herdr-obsidian) (the Obsidian plugin). Their contract is `PROTOCOL.md`: keep it in step with the routes and messages below, and keep changes additive, since old apps stay installed. The bridge binds `127.0.0.1` by default and `plugin/install.sh` runs `tailscale serve --bg --tcp 7788 tcp://127.0.0.1:7788` to bring the tailnet to it (`install.sh --lan` binds `0.0.0.0` instead, where the token crosses the network in clear text). Tailscale decides who can reach it, and a token decides who may use it: every request but `/health` carries `Authorization: Bearer <token>` (`require_token`; `src/token.rs` makes it on first start in `~/.config/herdr-bridge/token`, mode 0600, and refuses one others can read; `herdr-bridge --print-token` prints it; 8 characters like `K3MF-9QXA`, matched ignoring case, spaces and dashes). A wrong token is answered after a second, one at a time however many arrive (`REFUSALS`), which is what keeps 8 characters from being guessed. Without it, other users on the bridge's machine or on the tailnet could type into every pane. `GET /api/auth` answers 401 or 200, which is how an app tells a refused token from a bridge that's down. The checks run before `pick_machine`, so a refused request never connects to a remote machine. The bridge refuses any request carrying an `Origin` header (`reject_browsers`), since browsers let any web page open a WebSocket to any address and the apps' clients send none. It also refuses a `Host` that is a dotted name other than `*.ts.net` (DNS rebinding: a same-origin GET carries no `Origin`), so machines must be added by IP, bare name or MagicDNS name.

It also serves the machines saved in that herdr (`herdr machine list`) over SSH, so they need neither Tailscale nor a bridge of their own. Every machine needs herdr 0.9.2 or later (written against 0.9.5): `terminal.mouse` (taps) and agents' `completion_seq` ("finished" alerts) came in 0.9.2, and a remote machine's own herdr answers for it, since the bridge runs it there.

## Commands

```bash
cargo build --release
cargo run -- --port 7788        # the default bind is 127.0.0.1; flags also read from env: HERDR_SOCKET, HERDR_BRIDGE_BIND, HERDR_BRIDGE_PORT
RUST_LOG=herdr_bridge=debug cargo run
plugin/start-bridge.sh          # binds 127.0.0.1 (or HERDR_BRIDGE_BIND); runs ~/.local/bin, target/release, target/debug or PATH
```
`cargo test` runs the bridge's few unit tests (`usage.rs`, `token.rs`, `vault.rs`). `plugin/` is also a herdr plugin (`herdr-plugin.toml`: popup panes running `install.sh`, `install.sh --phone` and `install.sh --status`; `herdr plugin install XicuM/herdr-bridge/plugin`). `plugin/install.sh` asks what to set up, or takes `--bridge`, `--app`, `--phone`, `--lan`, `--status`. `--app` unpacks herdr-mobile's release Linux tarball into `~/.local/lib/herdr-mobile`; `--phone` prints QR codes (`qrencode`) for herdr-mobile's APK and for the pairing link `herdrmobile://pair?to=host:port&token=…&name=…`, which the app's Address field takes pasted or scanned. `--bridge` installs the binary (a local release build, else this repo's release, else `cargo build`) and `start-bridge.sh` to `~/.local/bin` and sets up `herdr-bridge.service` (systemd user unit, which sets its own `PATH` so `herdr`, `git` and `tailscale` resolve) or `dev.herdr.bridge.plist` (launchd, logging to `~/Library/Logs/herdr-bridge.log`).

CI (`.github/workflows/release.yml`) runs `cargo test` and `cargo build --release` on native ubuntu-22.04 x86_64 and arm runners, on every push to main, on pull requests, on `v*` tags and by hand. On a tag it attaches `herdr-bridge-linux-{x86_64,aarch64}` to the GitHub release. The license is GPL-3.0-or-later.

`herdr-bridge obsidian open <path>[#heading] [--line N]` is a client of the running bridge, not a server: it posts to `/s/herdr-obsidian/api/obsidian/open` on `127.0.0.1` with a bare HTTP request (the one call isn't worth a client crate), authenticating with the token file.

## Architecture

**Data flow** (`src/`):
- `herdr.rs` `HerdrClient`: each `call()` opens a new Unix socket connection (`send`), or for a remote machine (`HerdrClient::remote`) runs `ssh <target> herdr remote-api-bridge` (herdr's hidden stdio pipe to that machine's socket, as `herdr --machine` uses; with `--session` for a machine saved with another session; herdr's own commands there get it too), writes one newline-delimited JSON request `{id, method, params}`, and reads one response line, failing after 10 s. `snapshot()` wraps `session.snapshot`, drops what the app doesn't read and would push it a snapshot every second or two (`layouts`, whose scroll offsets move, and the raw `terminal_title` wherever a `terminal_title_stripped` exists, since Claude Code's spinner turns in it), adds each agent's `usage`, read on the bridge's own machine even for a remote machine's agents, since it's the same account everywhere (`usage.rs`, from the agents' own transcripts and usage files and their providers' usage endpoints, read on a blocking thread only for an agent whose pane a `/ws/term` streams (`HerdrClient.open`), the only place the app shows it, at most every 30 s (Anthropic's usage endpoint, which answers 429 to more, every minute; `agy`, which starts its MCP servers, every 5 min); limits not read for 3 min, or whose window has reset, are left out, and so are other tools' usage files not written in 3 min, so the app shows them as unknown rather than old; no made-up limits), adds each workspace's `git_branch` (one `sh` running `git branch --show-current` in each directory; left out when empty), and marks an agent `monitoring` while herdr calls it `idle` but its pane still runs background jobs (`monitors.rs`: one `/proc` walk under each pane's shell, this machine only, cached 10 s; herdr's screen detection only counts Claude's background agents and MCP tasks as working, not its background shells or watch loops), which the app shows as Monitoring…. `command()` runs a program on the machine: locally, or over SSH with every argument quoted and `~/.local/bin` on `PATH`, sharing one SSH connection (`ControlMaster`, `BatchMode`, so the key must work without a prompt; its socket goes in `XDG_RUNTIME_DIR`, else `~/.ssh`, never a shared `/tmp`, where another user could plant one). Server routes pass most calls straight through via `server.rs` `rpc`; POST routes whose body is herdr's params are `pass("method")`. A separate long-lived connection runs `events.subscribe` and fans the events out through a `tokio::broadcast` channel. It reconnects forever, backing off to once a minute while it fails; that also covers herdr closing a subscription that fell behind (`events_lost`).
- `server.rs` routes, for this machine at `/` and for each machine saved in herdr at `/m/<id>/` (`pick_machine` cuts the prefix before routing and hands the routes that machine's `AppState` as an `Extension`; a remote's event listener and poller start on its first request):
  - `GET /health`, `GET /api/snapshot`, `GET /api/machines` (the saved machines: `id`, `label`, `target`), `POST /api/machines` `{target, label}` → `herdr machine add`, `POST /api/machines/{id}` `{target, label}` → `herdr machine rename`, and for another target `machine add` (same session) then `machine remove`, since herdr can't change a target (the machine gets a new id), `DELETE /api/machines/{id}` → `herdr machine remove`
  - `POST /api/tab`, `DELETE /api/tab/{id}`, `POST /api/tab/{id}/rename`, `POST /api/tab/move` → `tab.move`, `POST /api/pane/clear` → `pane.clear` (screen and scrollback, keeping the prompt line), `POST /api/workspace` (plus workspace delete/rename, `POST /api/workspace/move` → `workspace.move_block`, and worktree routes), `POST /api/uploads` `{mime, data}` (base64 image → saved where that machine's agents run, answering its `path` for `@`-references; magic-checked, capped, pruned)
  - `WS /ws/session`: sends the snapshot as `{"type":"snapshot","data":…}` on connect (fetched for that phone) and then whenever it changed; with no snapshot it sends `{"type":"error","error":…}` instead (herdr down; for a remote, herdr's own reason from `herdr machine status <id> --json`, plus the `herdr machine reconnect` to run when SSH wants a password or MFA; else the bridge's own error). One shared poller (`start_snapshot_poller`, a `watch` channel in `AppState`) serves every phone and runs only while one is connected: right after any Herdr event (a burst makes one snapshot), and every 1.5 s. The poll is needed because herdr's global `events.subscribe` carries no agent status changes (`pane.agent_status_changed` requires a `pane_id`).
  - `WS /ws/term/{id}?cols&rows`: a real terminal stream. It first calls `pane.focus`, the only thing that marks a pane seen in herdr (`done` turns `idle`; the attach alone doesn't), so the desktop follows the phone. Then it spawns `herdr terminal session control <pane>` and relays its base64 frames as binary WS frames. It never takes the pane over unasked: while another client holds it herdr refuses, the bridge forwards that as a `{"type":"term-closed","reason":…}` text frame (plus the reason written into the terminal), and the app shows an "Another client is viewing" banner with a Take over button (`?takeover=1`, stealing the pane once) while retrying slowly instead of fighting it. Binary frames in are terminal input. A text frame with a `type` (e.g. `{"type":"terminal.scroll","direction":"up"|"down","lines":N}`) goes to herdr as-is; one without is a resize `{"cols","rows"}`. The frames out are herdr's *rendered viewport* (clear screen plus absolute cursor moves, no newlines), so the client never accumulates scrollback: history lives in herdr and is reached with `terminal.scroll`. On close it sends `terminal.release` so the desktop gets its size back. When herdr can't start or ends the session (`terminal.closed`'s `reason`, or its stderr), that text goes to the terminal as a frame. A pane id starting with `-` is refused, since herdr's parser has no `--`.
- Herdr payload shapes are handled loosely: code accepts both `snapshot.snapshot` and a bare snapshot, and alternate field names (`terminal_title_stripped`/`terminal_title`, `status`/`agent_status`). Keep that tolerance unless you've confirmed the real schema.
- `vault.rs` serves Obsidian vaults for the plugin's sync from a phone (`GET /api/vault/manifest`, `GET/POST/DELETE /api/vault/file`, `?vault=` naming the vault): the vault is the one called that in Obsidian's own list (`~/.config/obsidian/obsidian.json`, matched by its folder's name), never a folder a pane happens to be in. `vault::Watcher` (one for all machines, in `AppState.vault`) watches every vault in that list with `notify` (inotify), recursively, adding vaults new to the list as a `/ws/session` connects, and pushes `{"type":"vault_changed","vault","files"}` on every `/ws/session` half a second after a burst of writes ends (at most 2 s into one). Access events are dropped: listing a folder opens it, which would otherwise report it again forever. A folder created or moved in is walked, since notes written into it before it was watched raise nothing. A path is reported deleted only when it is gone, never on another read error, since the phone deletes its copy. Manifest entries carry `mtime_ms` beside `mtime` (seconds), so two writes within a second differ. Responses are gzipped (`CompressionLayer`): a manifest shrinks about eightfold. Hidden folders (`.obsidian` too: its settings are per device, and hold the plugin's bridge token) and build folders aren't synced; the plugin's `isSyncablePath` matches `is_syncable`.
- `POST /api/obsidian/open` `{file, heading?, line?}` (`file` absolute): `vault::vault_of` finds the vault holding it (the innermost, when one is inside another; `..` refused) and the bridge pushes `{"type":"open","vault","path","heading","line"}` on that session's `/ws/session` (`AppState.opens`, a `broadcast` channel, so only plugins connected to the `herdr-obsidian` session hear it). With none connected it answers 409, so the agent hears it. The plugin of another vault ignores the message by its `vault`.
